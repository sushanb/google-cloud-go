Agentic Development on the
Bigtable Session Subsystem

How two spec files, two subagents, and one hook keep Claude from drifting off Java parity or muddling components — on a codebase of ~36k lines of session/vRPC infrastructure.

google-cloud-go · bigtable/ · sushanb · 2026-07-10

The problem

Left alone on a large codebase, an agent drifts.

Two things happen quietly when an agent works session code without a pinned spec:

Java parity drift

The Go client is one of two implementations of the Session protocol. Every deviation from Java (heartbeat timing, retry classification, PeerInfo ordering, close-reason semantics) becomes an operator-visible cross-language bug. Agents don't cross-check Java by default.

Component muddling

internal/session starts importing bigtable.Row. Diverter grows per-method logic. Session holds pool-level counters. Each shortcut collapses a layer boundary and cements a design mistake that's expensive to unwind.

Neither problem manifests immediately. The tests pass, the PR reviews look clean. The debt shows up months later when Java rolls a change and the Go client can't follow — or when a refactor requires unwinding a cross-layer dependency that shouldn't exist.

The approach

Two specs. Two layers. Never mixed.

SESSION_SPEC.md

17 behavioral invariants. How each layer must *behave* at runtime.

  • #1–#10: single-Session behavior (state machine, in-flight limit, PeerInfo timing, hooks, close/GOAWAY, heartbeat rules, missed-heartbeat sequence, retry oracle, concurrency)
  • #11–#14: pool topology + routing (read/write pool split, shared channel pool, GetClientConfiguration authority, Diverter+TableShim)

Each item cites Java line-by-line where parity matters.

SESSION_COMPONENT_SPEC.md

12 boundary rules + ownership matrix. How the layers must *compose*.

  • Part A: layer map (reference, drifts with code)
  • Part B: 12 MUST rules — import direction, type leakage, ownership duplication, lock ordering
  • Part C: ownership matrix — sole owner per concern

Part B rules are grep-checkable. Part C prevents duplicated state.

The behavior file says what each layer must do. The component file says where each layer lives. Neither answers the other's question. Mixing them re-introduces the muddling they're meant to prevent.

Wiring

Four surfaces enforce the specs.

All four hang off the two spec files at the repo root. Removing any one leaves a gap; keeping all four is the durable minimum.

1. Always-loaded CLAUDE.md points to both spec files; loads on every session start. Trigger paths (internal/session/** etc.) named explicitly.
2. Just-in-time reminder PostToolUse hook fires after every Edit/Write on session-touching paths. Injects a system reminder: "verify against both specs."
3. Behavioral review session-reviewer subagent. Diff → 17-invariant table → pass/fail/violate with cited spec lines.
4. Boundary review session-component-review subagent. Diff → grep-checks + ownership walk → violations with fix suggestions.

Load path

CLAUDE.md is loaded into every session's context. It names both spec files and the file patterns that trigger a read. Claude opens the specs *before* editing, not after.

Enforcement path

Hook + subagents catch what the load path missed. Hook fires unconditionally on session-file edits; subagents run on demand before commit or as a Stop-hook.

Protection #1 — Java parity

Every parity-critical rule cites its Java source line.

The spec is not aspirational. Each Java-derived invariant carries a live citation into ~/google-cloud-java/java-bigtable/ (sparse local checkout).

The session-reviewer agent's instructions say: "If a change would create a deviation from Java, flag as VIOLATION unless the diff explicitly justifies the divergence." The agent has file-system access to the Java checkout and greps locally — no GitHub round-trip.

Protection #2 — No cross-component muddling

Boundaries as MUST rules, grep-checkable.

Part B of SESSION_COMPONENT_SPEC.md encodes twelve rules that the session-component-review agent enforces. The strongest ones reduce to a single git grep.

B1 — Proto-native session package

internal/session/** MUST NOT reference bigtable.Row, Mutation, Filter, etc.

git grep -l 'bigtable\.\(Row\|Mutation\|Filter\)' \
  bigtable/internal/session/
# MUST return empty

B2 — Import direction

internal/transport MUST NOT import internal/session. Session depends on transport, never the reverse.

git grep -l 'internal/session' \
  bigtable/internal/transport/
# MUST return empty

B4 — Diverter is shape-agnostic

One input (SessionLoad), one output (UseSession()). No per-method routing (that's TableShim). No per-row stickiness.

Adding a new vRPC method requires zero Diverter change.

B6 — Sole config writer

Diverter.SetSessionLoad and SessionPoolImpl.UpdateConfig callable only from ClientConfigurationManager.

git grep -n 'SetSessionLoad\|UpdateConfig' -- \
  ':!*_test.go' \
  ':!*_configuration_manager.go'

Protection #3 — Ownership matrix

One concern, one owner.

Part C names the sole owner of every stateful concern. Duplicating that concern elsewhere (defensive cache, redundant counter) is a rule violation, not an optimization.

ConcernSole ownerWhat violation looks like
Session state (New/…/Closed) Session.state (atomic) Pool caches "is-ready" separately; drifts on race
AFE ID Session.peerInfo (set once) Pool holds parallel map[sessionID]afeID; stale after reconnect
Per-AFE refCount, PeakEwmas afeHandle Session grows per-AFE fields; pool must iterate every Session to aggregate
Traffic split ratio Diverter.sessionLoadBits Application code calls SetSessionLoad; polled config no longer authoritative
Retry classification session_vrpc.go tag sites RetryingVRpc invents its own retry decision from raw gRPC codes
Proto ↔ public-type translation TableShim + sessionTable Session package references bigtable.Row

Each row is a review question: "Did this change add a field or method that duplicates an owner in this matrix?" If yes, either delete the duplicate or update the matrix with justification.

SESSION_SPEC.md

14 runtime-behavior invariants.

#1State machine strictly forward, 6 states, monotonic ordinals.
#2Exactly one in-flight vRPC per session; rpc_id-mismatched responses dropped.
#3PeerInfo/AFE ID resolved synchronously before Ready is announced.
#4Lifecycle hooks fire in fixed order, exactly once each.
#5Close idempotent; graceful drains in-flight; ForceClose does not.
#6GOAWAY does NOT cancel in-flight vRPC.
#7Heartbeat armed only while a vRPC is in flight; 3× interval; unknown frames don't reset.
#8Missed-heartbeat sequence is fixed and observable (5 steps).
#9Server is retry oracle; three-value AttemptState; zero = do-not-retry.
#10Concurrency discipline: Go atomics + sendMu; Java SynchronizationContext.
#11Read + write pools per resource; MatView is read-only.
#12One shared channel pool per SessionClient; distinct from classic pool.
#13GetClientConfiguration is authoritative for pool load and shape.
#14Diverter (policy) + TableShim (mechanism) split traffic session vs classic.
#15All /-z debug pages MUST NOT block hot-path latencies.
#16cluster_id/zone_id/transport peer per-attempt on BOTH paths, path-specific sources.
#17Pool scaling is server-driven with rate-limiting; scale-down is passive (Java-parity replace-on-close).

Blue = per-Session behavior (#1–#10). Orange = pool topology + routing + observability + scaling (#11–#17). The two are enforced separately and never mixed inside a single component.

SESSION_COMPONENT_SPEC.md — Part B

12 boundary MUST rules.

B1internal/session/** MUST stay proto-native. No public bigtable types.
B2internal/transport/** MUST NOT import internal/session.
B3debugview/** reaches state only via SessionDebugProvider.
B4Diverter MUST stay RPC-shape-agnostic.
B5TableShim MUST NOT reach into Session/pool internals.
B6ClientConfigurationManager is the sole writer of pool-shaping config.
B7Session MUST NOT hold pool-level counters.
B8Pool → SessionList lock ordering fixed.
B9Retry classification lives at the vRPC boundary, not in Session/pool.
B10z-page code MUST NOT synthesize state computable on the producer.
B11Behavioral invariants MUST NOT be re-implemented in another layer.
B12Session-level and pool-level invariants MUST NOT mix in one component.

Rules B1, B2, B3, B6 reduce to git grep commands the session-component-review agent runs verbatim on every review. The result is binary: any match on those greps is an immediate DO NOT COMMIT.

The end-to-end workflow

Edit → hook → dual review → merge.

1. Load Session starts. CLAUDE.md loads. Claude sees the pointer to both specs and reads them before touching session code.
▶
2. Edit Change to bigtable/internal/session/table.go. Edit tool returns.
▶
3. Hook PostToolUse matches path, injects system reminder: "verify against both specs."
▶
4. Dual review Claude spawns session-reviewer + session-component-review in parallel.
5a. All PASS Both agents report PASS tables. Claude proceeds to commit + push.
5b. Any VIOLATION Agent returns "DO NOT COMMIT" with cited rule + minimum fix. Claude applies the fix, re-runs the reviewer, loops until PASS.

The user is in the loop, not the bottleneck. The reviewers automate what would otherwise be a "did you check the 14 invariants?" question on every PR. The user reviews the reviewer output, which is dramatically smaller than the diff.

When a spec becomes stale

Both agents flag spec edits that lack code, and vice versa.

The specs are living documents. They MUST evolve — but drift-of-convenience is the failure mode we're preventing.

Rule for spec edits

Editing SESSION_SPEC.md requires either:

  • an accompanying code change that motivates it, or
  • an explicit justification in the PR body (design decision, Java catch-up, protocol update)

Both reviewer agents check this and refuse a "silent" spec edit.

Rule for code changes that appear to violate the spec

Two options:

  1. The code is wrong — fix it.
  2. The spec is stale — update the spec in the same PR, cite the reason, get mutianf's sign-off on human-reviewer PRs.

Never merge code that silently deviates. The spec is either right or updated; there's no "temporarily out of sync."

Part A of SESSION_COMPONENT_SPEC.md is the exception — it's the file-path reference map, explicitly labeled "expected to drift." Editing Part A to catch drift is fine and needs no accompanying code change. Editing Part B or Part C without code is a smell.

Before / after

What this replaces.

Before: memory-driven

  • Invariants live in the author's head + a scattered ~/.claude/plans/ collection
  • Each session, Claude re-derives them from grepping the code
  • Java parity checked ad-hoc when someone remembers
  • Cross-component leaks caught in code review, weeks later
  • New teammates onboard by asking "what should I not break?"

After: spec-driven

  • 17 behavioral invariants + 12 boundary rules pinned in two files at repo root
  • CLAUDE.md loads on every session; Claude reads specs before editing session code
  • Java parity flagged automatically by session-reviewer against local Java checkout
  • Cross-component leaks caught immediately by session-component-review greps
  • New teammates read two files and know the contract

Net effect: Claude's default behavior on session code shifts from "make the tests pass" to "make the tests pass without violating the 14 invariants or the 12 boundaries." That's the whole point.

Summary

Four artifacts. Two axes of enforcement. One live loop.

Artifacts

SESSION_SPEC.md

SESSION_COMPONENT_SPEC.md

SESSION_SPEC_TESTS.md

.claude/agents/ (2 files)

.claude/settings.json (hook)

Enforcement axes

Behavior: session-reviewer against 14 invariants.

Structure: session-component-review against 12 boundary rules + ownership matrix.

Neither reviews the other's territory.

Loop

1. Load — CLAUDE.md

2. Trigger — PostToolUse hook

3. Verify — both subagents

4. Merge — if all PASS

5. Evolve — specs update alongside code, never silently

The mechanism is boring on purpose. There is no clever ML in the loop. Two markdown files, two subagent prompts, one shell hook. Every piece is auditable, editable, and grep-checkable. That's what makes it durable.
