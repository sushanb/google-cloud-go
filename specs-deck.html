One-shot prompting — when the change fits in one breath

Definition. A single 3–4 sentence prompt with enough context to land a bounded refactor in one iteration — no back-and-forth, no plan mode, no subagent orchestration. The reviewer’s question is simple: “does this look right?”, and the diff is small enough to answer.

Three PRs that shipped this way

PRTitleWhat changed
#19987 Modularize DirectAccessChecker DirectPath was hard-wired into the unary channel-pool path. Extracted the check into a DirectAccessChecker interface with a pingAndWarmDirectAccessChecker impl, so a session-side sibling (getClientConfigDirectAccessChecker) can plug in later.
#20027 Modularize ChannelPrimer Per-connection Prime was coupled to the unary channel pool. Extracted into a ChannelPrimer interface with a pingAndWarmChannelPrimer impl. A nil primer becomes the session pool’s “no priming” mode.
#20099 Client-side metrics decoupled from unary Metrics stamping assumed a gRPC unary interceptor context (headers/trailers, OutPayload stats event). Extracted the per-attempt stamp interface so the session (vRPC) path can source the same labels from a typed InvokeResult instead of gRPC callbacks.

Why one-shot worked here

  • One concept per PR. Each extracted a single implicitly-unary abstraction into an interface. The scope was crisp; the prompt fit in a paragraph.
  • Behavior preserved by construction. The unary caller kept its concrete impl; the interface was a pure extraction. No semantics changed.
  • Reviewer can hold the whole diff in head. A ~200-line PR with one new interface + one impl + one call-site rewire is checkable end-to-end.

Common shape. Extract-then-inject. Each PR was 3–4 sentences of prompt describing the target interface + the two impls to wire up. That’s the ceiling for what one-shot can carry — and it stops carrying the moment the change spans invariants that live in the reviewer’s head instead of on paper.

Then came Jetstream — 30k+ LOC, no shared axis

The scale problem. Session lifecycle + AFE picker + Diverter + z-pages + client-side metrics + pool scaling, all in flight. Tests included: > 30k lines. A single prompt can’t carry the required context. Every code iteration devolves into “does this look right?” — there’s no shared axis, no way to prove a change preserved an existing rule.

Concrete failure mode. A one-line “fix” that cancels the in-flight vRPC on GOAWAY looks harmless in isolation — but it flips a successful non-idempotent Apply into a client-visible TransportFailure. Nothing in the diff says “this invariant existed.” The rule lived only in the reviewer’s head.

The fix: write the invariants down, split by concern

Five spec files at repo root. Each governs one layer of the subsystem. Each numbered invariant is a MUST-rule with a name, a body, and grep-checkable file:line citations. Reviewer subagents read the spec, walk the diff, and report PASS / VIOLATION / AMBIGUOUS per invariant.

Spec fileInvariantsExample rule
SESSION_SPEC.md 10 #6 — GOAWAY does NOT cancel the in-flight vRPC (Java parity: SessionImpl.java:689-716). Server may still deliver the response — critical for non-idempotent Apply.
SESSION_CLIENT_SPEC.md 4 #3 — GetClientConfiguration is the authoritative source for pool sizing / LB / traffic split. Poll is monotonic (configSeq); listeners drop older callbacks.
SESSION_POOL_SPEC.md 5 #2 — AFE picker uses e2eEwma, NOT transportEwma (Java parity: LeastLatencyPicker.java:59-60). PeakEwma updates are OK-gated so fast-failing AFEs don’t game the picker.
CLIENT_SIDE_METRICS_SPEC.md 3 #2 — Session-path latency labels sourced only from InvokeResult; sessionTable.stampAttempt is the single writer. Classic path uses gRPC callbacks; must not be simulated on session side.
SESSION_COMPONENT_SPEC.md 12 boundary + Part C ownership B2 — bigtable/internal/transport/** MUST NOT import bigtable/internal/session. Enforced grep: git grep -l 'cloud.google.com/go/bigtable/internal/session' bigtable/internal/transport/ returns empty.

Why this shape. The spec is living — updated in the same PR as the code it governs. Java-parity notes make cross-language drift visible. Numbered invariants become the shared axis reviewers were missing.

SESSION_COMPONENT_SPEC.md — structure, boundaries, ownership

The component spec is different from the four behavioral specs. It governs structural layout — who owns what, what MUST NOT import what, where responsibilities live. Three parts:

Part A — Layer map (descriptive, drifts with code)

Seven layers, bottom-up. Reviewer uses this as a starting point for grep, not as authoritative citations.

#LayerLocation
1Transport primitivesbigtable/internal/transport/ — Stream, State, AttemptState
2Sessioninternal/transport/session*.go — Session, SessionHooks, afeID
3Pool + Pickerinternal/transport/session_pool*.go, afe_picker.go — SessionPoolImpl, sessionList, afeHandle, PoolSizer
4Session client + tablesbigtable/internal/session/ — SessionClient, SessionTableApi, lazyPool, ClientConfigurationManager
5Routing shim + divertertable_shim.go, internal/transport/diverter.go (Go-only mixed-mode)
6Public bigtable APIbigtable/ — Client, Table, Mutation, Row
7Observability tierbigtable/debugview/, *_snapshot.go — provider interfaces + snapshot DTOs + 7 z-pages

Part B — 12 boundary MUST-rules (prescriptive)

RuleWhat it forbidsHow it’s checked
B1internal/session/ importing public bigtable types (Row, Mutation, Filter, …)Grep in spec; import cycle blocks the top-level package.
B2internal/transport/ importing internal/session/Go’s cycle detector at build time (session already imports transport).
B3debugview/ importing concrete pool/session typesReviewer agent grep.
B4Diverter gaining per-method or per-key routing (must stay shape-agnostic)Reviewer agent surface check.

…4 more rules cover Diverter/TableShim surfaces (B5), retry-boundary discipline (B9), z-page non-computation (B10), and two meta-rules on not re-implementing behavioral invariants (B11, B12).

Part C — Ownership matrix (sole owner per concern)

Every mutable concern names exactly one owner. Others read via accessor/interface; no parallel copies.

In-flight vRPC slot | Session.activeRPC (atomic CAS) | pool MUST NOT track “which session has an outstanding call” separately.

Traffic split ratio (session vs classic) | Diverter.sessionLoadBits (atomic float64) | driven by ClientConfigurationManager.SessionLoadListener.

Per-attempt ClusterInfo (session path) | InvokeResult.ClusterInfo (returned by Session.Invoke) | stamped by sessionTable.stampAttempt; MUST NOT be re-derived from headers.

Session-tracer OTel histograms (session.durations, session.open_latencies, session.uptime, transport_latencies) | sessionTracer; registered once by InitializeSessionMetrics | sole writer; transport_latencies only from session_pool.go:650 under the positive-delta gate.

Why three parts, not one. Part A drifts with the code and everyone knows it. Part B is the durable prescriptive layer — violations block PRs. Part C names sole owners so a future contributor can’t innocently add a second writer that silently drifts labels or state.

Three prompts, three sizes — same review mechanism

The spec + hook + reviewer pattern scales across change size. What varies is how much reviewing happens; the mechanism is identical.

1 Simple refactor — typed accessors for an atomic field

“Add a getter and CAS wrapper for Session.activeRPC (atomic.Pointer[vrpcImpl]) so call sites don’t reach the atomic directly. Route all 11 production .Load() and .CompareAndSwap() sites through the wrappers; leave test .Store() sites direct (fixture setup only).”

Flow. Pure passthrough refactor. Hook fires per edit. Before commit → session-reviewer confirms the CAS invariant (SESSION_SPEC.md #2) is preserved bit-for-bit; session-component-review confirms no boundary crossings and no ownership change (Part C row for “In-flight vRPC slot” unchanged). Both PASS → commit.

2 Logic addition — adaptive session-creation throttler (Java-parity budget)

“Add adaptive session-creation throttling. New SessionThrottler interface with an AdaptiveSessionThrottler impl: a semaphore bounds concurrent OpenSession attempts; on failure the released slot pays a NewSessionCreationPenalty before re-entering the concurrency pool. Match Java SessionCreationBudget.java. Wire into SessionPoolImpl.openSession. Three server-driven knobs: NewSessionCreationBudget, NewSessionCreationPenalty, ConsecutiveSessionFailureThreshold (circuit breaker).”

Flow. Touches session_creation_budget.go (new impl), session_pool.go (Acquire/Release around OpenSession), client_configuration_manager.go (proto parsing + UpdateConfig). Multi-file, spans several invariants:

  • SESSION_POOL_SPEC.md #5 — the “server-driven scaling MUST NOT overwhelm the control plane” invariant exists because of this throttler. Reviewer checks: budget acquired before OpenSession? Failed release pays the penalty (`RetryingVRpc`-style hint from server not honored elsewhere)? Consecutive-failure circuit breaker trips at threshold?
  • SESSION_CLIENT_SPEC.md #3 — the three knobs come from GetClientConfiguration; throttler MUST be tuned via UpdateConfig, not locally.
  • SESSION_COMPONENT_SPEC.md B6 — throttler.UpdateConfig called only from ClientConfigurationManager’s listener. Grep-checkable.

Reviewer PASS confirms the invariant chain end-to-end — a future contributor cannot bypass the budget with a direct go pool.openSession(...), and cannot tune the penalty from application code.

3 Big feature — unified debugview/ (7 z-pages behind one Handler)

“Fold sessionz / afez / loadz / channelz / configz / tcpz / debugtagsz into a single bigtable/debugview/ package with one mount point: mux.Handle("/debug/", http.StripPrefix("/debug", debugview.Handler(client, tcpStats))). Every z-page reads pool/session/channel/config state only through the three provider interfaces (SessionDebugProvider, ChannelDebugProvider, ConfigDebugProvider) — no concrete *SessionPoolImpl or *Session imports. Both args nil-safe: nil client → “not enabled” state; nil tcpStats → “collector detached”. Root / renders a link index. Every view supports ?format=json.”

The seven live pages. sessionz (per-pool sessions + states + latency histograms + slow-vRPC log + scaling history), afez (per-AFE bucketing: refCount / idle / in-use / EWMAs), loadz (picker decision reasoning + K-choice trace), channelz (gRPC channel pool state), configz (server-driven client configuration), tcpz (per-connection TCP_INFO), debugtagsz (process-global debug-tag counters).

Why the specs made this survivable. The refactor collapsed 7 previously-separate packages (each with their own handler + snapshot code) into one, while preventing the “let me just peek into the pool struct” shortcut that would’ve made every future pool refactor break the UI:

  • SESSION_COMPONENT_SPEC.md B3 — debugview/ MUST access pool/session state ONLY via SessionDebugProvider (and siblings); MAY import snapshot DTO types (PoolSnapshot, AfeSnapshotRow, …) but NOT the concrete *SessionPoolImpl. This rule exists because of this refactor.
  • SESSION_POOL_SPEC.md #4 — z-pages MUST NOT block hot-path latencies. Snapshot methods take at most RLock, copy fields, release before returning; z-page holds no lock across the HTTP write. A hung z-page cannot hang the process.
  • SESSION_COMPONENT_SPEC.md B10 — z-page code MUST NOT synthesize state that could be computed on the producer. Derived values (session age, in-flight duration) live on the snapshot DTO, not in the HTML template — so a second consumer (JSON API, test) gets the same values.
  • Interface stability, verified by the reviewer. Adding a 4th method to SessionDebugProvider? Every fake in afez_test.go / sessionz_test.go / loadz_test.go must implement it. Interface is defensive by design.

What the spec catches on new z-pages. A future flightz2 that reaches into *SessionPoolImpl.waiters directly — VIOLATION on B3. A template that computes time.Since(sess.OpenedAt()) instead of reading a pre-computed Age DTO field — VIOLATION on B10. A handler that sits on p.mu.RLock() across w.Write(…) — VIOLATION on POOL #4. Reviewer catches all three from grep-checkable rules; without the specs each would be “hmm, seems fine” in code review.

How reviewers use the specs

Two agents in parallel, per commit

  1. session-reviewer — reads all 4 behavioral specs, walks the diff, reports one row per touched invariant: Spec | # | PASS / VIOLATION / AMBIGUOUS | Evidence (file:line).
  2. session-component-review — reads SESSION_COMPONENT_SPEC.md, checks boundary rules (B1–B12) and Part C ownership; runs the grep patterns documented in the spec.
  3. PostToolUse hook fires on every edit to a session-scope file — the reminder is Claude’s cue to spawn both agents before git commit.

What PASS vs VIOLATION mean

  • PASS — the invariant holds after this change; commit.
  • VIOLATION — the code contradicts the spec. Either (a) fix the code, OR (b) if the rule is stale, update the spec in the same PR with justification.
  • AMBIGUOUS — the reviewer can’t decide from the diff alone; needs context (e.g., a Part C row is missing for a sole-owner claim you just added).

Load-bearing property: specs are living. When a rule is wrong, you update it in the same PR — never in a follow-up. That’s what keeps the reviewer’s citations honest.
